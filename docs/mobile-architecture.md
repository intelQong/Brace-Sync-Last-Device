# Mobile-first architecture for Brave last-device recovery

## Product goal

Build a privacy-preserving backup and recovery system for people using Brave Browser primarily on iOS and Android who do not want to lose recoverability when the last device in their Brave Sync Chain disappears.

The system must not require a browser extension. It should use cloud sync and encrypted recovery data instead.

## Reality check: mobile Brave is sandboxed

On desktop, a local agent can inspect browser profile directories. On iOS and Android, Brave's browser data is inside the app sandbox. Another app or background service generally cannot read it directly.

That means a mobile-first implementation needs a different model:

- Do not depend on reading Brave's private on-device files.
- Do not require root or jailbreak for normal users.
- Do not store plaintext Sync Chain secrets in GitHub, Cloudflare, app logs, screenshots, or analytics.
- Prefer user-mediated export, recovery metadata capture, and encrypted vault storage.

## Recommended architecture

```text
Brave iOS / Android
        |
        | user-mediated setup/export/recovery data
        v
Mobile recovery client or desktop companion
        |
        | encrypt locally
        v
Cloudflare R2 encrypted object vault
        |
        | encrypted manifest pointer only
        v
GitHub repository / GitHub Actions
```

## Components

### 1. Recovery client

The recovery client can be a native mobile app, a desktop CLI, or both. Its job is to collect only user-approved recovery data, encrypt it locally, and upload encrypted objects.

Responsibilities:

- Create a local recovery vault.
- Derive an encryption key from a passphrase or generated recovery key.
- Encrypt recovery material before upload.
- Upload encrypted blobs to Cloudflare R2.
- Download and decrypt blobs during restore.
- Run restore verification without exposing secrets.

### 2. Cloudflare R2 encrypted vault

Cloudflare R2 should store encrypted backup objects.

Objects should include:

- Encrypted recovery manifests.
- Encrypted user-provided Brave Sync setup records.
- Encrypted bookmark/export files where available.
- Encrypted restore runbook snapshots.

R2 should not receive plaintext Brave data or plaintext Sync Chain material.

### 3. GitHub metadata layer

GitHub should not be the main storage for browser data. Use it for small, encrypted, non-sensitive operational metadata.

Good GitHub uses:

- Encrypted manifest pointer.
- Backup health status generated by automation.
- Retention policy configuration.
- Recovery documentation.
- Optional GitHub Actions workflow that checks whether expected encrypted R2 objects exist.

Bad GitHub uses:

- Plaintext Sync Chain words.
- Plaintext QR codes.
- Plaintext browser exports.
- Large browser profile archives.
- Secrets committed to the repository.

### 4. Optional Cloudflare Worker

A Cloudflare Worker can hide R2 credentials from the client by issuing short-lived upload and download URLs or by proxying authenticated requests.

Worker responsibilities:

- Validate GitHub OIDC or signed client requests.
- Generate short-lived R2 object access.
- Enforce object prefix isolation per user/device.
- Reject plaintext uploads if the client metadata does not mark the object as encrypted.

## MVP scope

The mobile-first MVP should implement:

1. `init-vault` flow for creating a recovery key.
2. `save-sync-recovery` flow for storing encrypted Sync Chain recovery material.
3. `save-export` flow for encrypted user-provided Brave exports.
4. `verify-vault` flow for downloading, decrypting, and checksum-validating the latest recovery bundle.
5. `restore-guide` flow that prints step-by-step instructions for rejoining Brave Sync or rebuilding available data.

## Data model

### Recovery manifest

The manifest is safe to store in GitHub only if encrypted, or if it contains no sensitive data.

Suggested fields before encryption:

```json
{
  "schema_version": 1,
  "created_at": "2026-06-05T00:00:00Z",
  "updated_at": "2026-06-05T00:00:00Z",
  "devices": [
    {
      "label": "iPhone",
      "platform": "ios",
      "brave_sync_enabled": true,
      "notes": "User-owned device"
    }
  ],
  "objects": [
    {
      "type": "sync-recovery-record",
      "r2_key": "vaults/example/sync-recovery-record.enc",
      "sha256": "...",
      "encryption": "aes-256-cbc-hmac-sha256"
    }
  ]
}
```

### Encrypted object envelope

Every object uploaded to R2 should include an authenticated envelope:

```json
{
  "schema_version": 1,
  "algorithm": "aes-256-cbc-hmac-sha256",
  "kdf": "scrypt",
  "salt": "base64",
  "iv": "base64",
  "ciphertext": "base64",
  "aad": {
    "object_type": "sync-recovery-record",
    "created_at": "2026-06-05T00:00:00Z"
  }
}
```

## Platform strategy

### iOS

For iOS, assume the app cannot read Brave's private data. The product should focus on:

- User-guided Sync Chain recovery recording.
- User-provided exports if Brave exposes them.
- Apple device backup compatibility notes.
- Restore runbooks.

### Android

For Android, assume the app cannot read Brave's private data on a normal non-rooted device. The product should focus on:

- User-guided Sync Chain recovery recording.
- User-provided exports if Brave exposes them.
- Optional Android backup/document picker integration if Brave exposes exportable files.
- No root-only feature as an MVP requirement.

### Desktop companion

A desktop companion remains useful because desktop Brave profile files are accessible to the signed-in user. If a user also has a desktop Brave device, it can create fuller encrypted backups. But this should be an optional enhancement, not a mobile MVP dependency.

## Security requirements

- Encrypt before upload.
- Use authenticated encryption.
- Generate unique nonces per object.
- Keep R2 and GitHub credentials separate from the vault encryption key.
- Never log plaintext recovery material.
- Never commit secrets to GitHub.
- Provide a verification command that proves the user can decrypt the latest vault.
- Warn users that losing both the Brave device and the vault recovery key means recovery is impossible.

## Non-goals for MVP

- Browser extension integration.
- Account-based Brave replacement sync.
- Rooted Android extraction.
- Jailbroken iOS extraction.
- Silent mobile browser database scraping.
- Plaintext backups.
